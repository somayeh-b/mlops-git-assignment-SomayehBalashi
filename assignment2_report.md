The most striking finding is the **phone number formula-injection issue**: values such as
`=1-312-654-7472` were entered with a leading `=`, which Excel/openpyxl interprets as a
formula and evaluates as arithmetic (`1-312-654-7472` = `-8437`), silently destroying the
original phone number in ~15% of records. This is a classic spreadsheet data-entry hazard
and a reminder to always load such source files as raw text, not through a spreadsheet
application that auto-evaluates formulas.

## Part 5: Reflection

**Most impactful data quality issue: corrupted/out-of-range `age` values**

Across the dataset, the `age` column has 147 missing values and 384 out-of-range values
(negative ages, ages like 999 or 300) — together **531 corrupted entries, ~10.6% of all
rows**. I consider this the most damaging issue for ML model performance, for these
reasons:

- **It silently distorts a core numeric feature.** Age is frequently used directly or in
  derived features (age bins, interactions). A handful of `999` or `-25` values will blow
  out any min-max scaling, badly skew the mean/standard deviation used by z-score
  normalization, and drag regression coefficients toward nonsensical values.
- **It is not simple to fix by dropping rows.** At 10.6% of the dataset, dropping every
  affected row discards a meaningful fraction of the training data and risks introducing
  bias if the corrupted rows are not missing-at-random (e.g. if a particular signup
  channel systematically produced bad age values).
- **The failure mode is silent, not loud.** Unlike a `NaN` that many libraries will flag,
  a technically-valid-but-wrong number like `age=999` passes type checks and only shows up
  as a problem once the model is already trained on it.
- **It compounds with the duplicate-ID and formula-injection issues.** Since 303 customer
  IDs are duplicated and could double-count the same corrupted age value, and the phone
  corruption shows the same file went through an Excel round-trip, there's a good chance
  the age anomalies come from the same spreadsheet-handling failure mode, not independent
  data-entry mistakes.

**Why other issues are comparatively less critical:** missing `country` (0.8%) and missing
`signup_date` (0.3%) affect small slices of the data and are easy to impute or drop.
Invalid country values (e.g. `Germany`, `India`) are simple to catch and either exclude or
remap. The row-count violation (5,015 vs. 500–1000) is a pipeline-configuration mismatch
rather than a per-record quality problem — it tells us the assumption baked into the
expectation suite was wrong, not that the data itself is unusable.

**Recommended fix**

```python
import pandas as pd

def clean_age(a):
    try:
        val = float(a)
    except (TypeError, ValueError):
        return None
    if val < 0 or val > 120:
        return None
    return val

df["age"] = df["age"].apply(clean_age)
# Impute remaining nulls with the median age rather than dropping ~10% of rows
df["age"] = df["age"].fillna(df["age"].median())
```

I would add this as a cleaning step in the pipeline before any model training, and log how
many rows were coerced to null so the scale of the issue stays visible over time rather
than being silently imputed away.
